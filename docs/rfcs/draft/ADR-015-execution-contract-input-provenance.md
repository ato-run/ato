# ADR-015 — Execution Contract input provenance, and the v1 authoring surface

- Status: **draft** (§6 decisions taken 2026-07-26)
- Date: 2026-07-26
- Supersedes: nothing. Completes `CAPSULE_V1_EXECUTION_MODEL_SPEC.md` §4.2/§4.6 and §6.
- Related: ADR-014 (Capsule Program Identity), ato#1089, ato#1086

---

## 1. Decision

**Only a `schema_version = "1"` manifest may mint a new Execution Identity in
production.**

- v0.3 is kept, unchanged, for existing `run` / `build` compatibility.
- There is **no implicit v0.3 → v1 conversion and no automatic migration**.
- An `execution_contract` is **never** generated by filling v0.3's ambiguous
  values with defaults.
- v1 lands as a **strict vertical subset** sufficient for Submission Wizard
  Step 4. Every feature outside that subset is refused explicitly, not
  approximated.

### Why this ordering

`ExecutionContractV1` has three *typed* facets whose values v0.3 cannot express
at all — not opaque payloads that could be defined later, but fields whose type
is already frozen:

| facet | v0.3 state |
|---|---|
| `guest_surface.bind_address` | not declarable anywhere; every occurrence in the tree is a `"0.0.0.0"` test fixture |
| `guest_surface.protocol` / `features` | not declarable; the real vocabulary lives in `protocol::session_surface`, unconnected to the manifest |
| `external_state.access` | no field exists; `ServiceStateBinding.mode` is an octal permission string, and the one real `BindingMode{ReadOnly,ReadWrite}` sits on `[bindings.*]`, which `derive_build_spec` rejects outright |

Defining payload schemas on top of that would fix `execution_id` — permanently —
for facts the authoring surface cannot state. The identity would be a claim
about something no author ever declared.

## 2. The provenance taxonomy

Every facet of `ExecutionContractV1` MUST be classified as exactly one of:

| class | definition | admissible source |
|---|---|---|
| **authored** | the author states it in `capsule.toml`; absence is either an error or an explicit, spec-defined value | the v1 manifest, verbatim |
| **resolved** | derived deterministically from authored inputs plus pinned resolution (lock refs, resolved artifacts) — no host state, no observation | the resolver, from authored + lock |
| **measured** | read from the concrete materialized build; recomputed by every party that verifies | bytes on disk / in the image |
| **normative default** | a value fixed **by this spec**, identical for every capsule, and stated here | this document |

### Rules that make the taxonomy load-bearing

1. **A fixture value is not a normative default.** `"0.0.0.0"` appearing in test
   fixtures is evidence of a *missing* declaration, never of a default. A
   normative default must be justified here, in prose, as the correct value for
   every capsule — not as the value that happened to be convenient.
2. **A convention is not a normative default.** "The init script always mounts
   `/tmp`" is a fact about the current builder, not a contract-level default; if
   it belongs in identity it must be stated here and become part of the
   contract's meaning.
3. **A facet with no admissible source is not classified — it is BLOCKED**, and
   the v1 subset must refuse any capsule that would need it.
4. **`resolved` may never silently become `measured`.** If a value is supposed to
   be recomputed from bytes, copying it from the lock is not verification
   (§4.6 of the spec).
5. **Authored ≠ resolved for the launch command.** See §3.

## 3. `authored command` vs `resolved launch.argv`

The Execution Identity identifies the **resolved, target-specific launch
envelope** — not the author's intent. These are two different things and this
ADR names them separately:

```text
authored command        v1 `[run] command` / `[[build.steps]] command`.
                        An argv ARRAY. Implicit shell forbidden. Argument
                        boundaries are the author's meaning and are preserved
                        exactly.

resolved launch.argv    The complete argv the runner actually starts, after
                        resolution. This is what `ExecutionContractV1.launch.argv`
                        records.
```

Recording `["/bin/sh", "-lc", "…"]` as a **resolved** argv is truthful when that
is genuinely what is executed. It becomes false only if presented as the argv the
author specified with preserved boundaries.

For v1 the two coincide by construction when the author's argv is executed
directly. Where resolution legitimately wraps or prefixes the command (a runtime
invocation prefix, an interpreter), the wrapping is part of the resolved envelope
and MUST be visible in `launch.argv` rather than hidden.

**v0.3's shell string is therefore not a lie about `launch.argv`** — it is an
accurate resolved argv. It is a lie about the *authored command*, which v0.3
cannot express as an argv at all. That is one of the reasons v0.3 does not mint.

### 4.3 Opaque payload facets — classified, schemas deferred to step 4

Each of the nine undefined payloads gets its schema in the payload-schema PR.
This ADR fixes only their **provenance class**, because that is what decides
whether a schema is definable at all:

| payload | class | rationale |
|---|---|---|
| `source.projection_digest` | N | the projection rules are entirely constant in v1 (a named, versioned profile). See §5 |
| `runtime.dynamic_contract_digest` | R | the resolved runtime's launch-time behaviour beyond its bytes |
| `build_outputs[].projection_digest` | A→R | requires a v1 authoring surface for *named* outputs and their guest placement; today outputs are unnamed and land in the host workspace → v1 subset REFUSES build outputs |
| `launch.process_model_digest` | A→R | single-process vs supervised is real data; restart/reaping/signal policy is NOT declarable → the v1 subset covers the single-process case and refuses the rest |
| `launch.environment_policy_digest` | A | requirements + normalization + inheritance; requires §4.4 below |
| `filesystem.topology_digest` | R | the mount table; three disjoint lanes exist and nothing composes them → v1 subset covers the no-volume topology and refuses volumes |
| `policy.network_digest` | A→R | egress/ingress are declarable; **DNS and isolation policy have no field at all** → the payload must either exclude them (and say so here) or the surface must add them |
| `policy.capability_digest` | A | the real vocabulary is `security::schema::capabilities::Capabilities`, whose own rule is "absence means not declared, do not infer a level" — that rule must survive into the payload |
| `policy.filesystem_digest` | A | no manifest-level filesystem policy exists at all today |

### 4.4 The config-classification fix (step 3 of the plan)

v0.3's `ConfigField` has **no `required` field** and `ConfigKind` defaults to
`Secret`; `resolved_config_schema` synthesizes a field per `required_env` name
using that default. The consequence is that a legacy capsule's entire env
surface classifies as *secret* — which under the contract means
`secret_bindings`, not `launch.environment[]`, and the contract rejects a name
that appears in both.

v1 therefore:

- states `kind` **and** `required` explicitly per config field;
- **does not reuse** the legacy `ConfigKind::Secret` default in the v1 producer;
- **rejects at generation time** any name belonging to both `environment` and
  `secret_bindings`.

## 5. The two source-projection domains are NOT merged here

`ato.source-projection-contract/v1` (`source.projection_digest`) and
`ato.capsule-program-source-projection/v1` (ADR-014, `ProgramSourceContract`)
are organized by ADR-014 as **different preimages in different domains**: the
former commits the projection presented to the *build*, the latter the
control-file-excluding projection used for *Program Identity*.

They are left separate. Merging them is admissible **only** after comparing the
implementations and establishing that the preimage is genuinely identical. An
earlier claim in this workstream that they were a duplicate naming was premature
and is withdrawn.

## 6. Decisions on the four questions

### 6.1 `guest_surface.protocol` — **resolved (`R`), no authoring field**

`protocol` is Ato's own surface-contract profile, not an application-layer HTTP
version the author chooses. It is therefore **resolved from the kind of surface
the manifest declares**, and there is no `[web] protocol` field.

Step-4 subset mapping:

```text
[web]   →   guest_surface.protocol = "ato.web-surface.v1"
```

`SessionSurfaceTransport` is a separate concept and is deliberately NOT folded
in. When Pixel and Terminal surfaces gain a v1 authoring form, this same mapping
table is extended — one table, so a surface can never acquire two spellings.

### 6.2 `guest_surface.features` — **omitted in the Step-4 subset**

Not a normative empty set. The field's meaning is:

```text
features omitted              no additional feature requirement
features present, non-empty   these features are required
features present, empty       INVALID
```

The `None` vs `Some([])` distinction is **not carried into the Execution
Contract**. v1 authoring rejects an empty array at the source, so the contract
never has to represent the difference.

A Step-4 input that would need a feature or profile is refused by name:

```text
UnsupportedGuestSurfaceFeatures
```

### 6.3 Absent vs empty — one global rule, plus array semantics

```text
null                              always forbidden
empty array / empty object        always forbidden
optional collection, 0 elements   omit the field
required collection               present and non-empty
```

Arrays additionally split by whether order carries meaning:

| kind | facets | rule |
|---|---|---|
| **ordered** | `launch.argv`, `build.steps` (authoring), `filesystem.readonly_layers` | preserve the authored / resolved order verbatim |
| **set-like** | `guest_surface.features`, `launch.secret_bindings`, `target.observable_features`, and every other unordered collection | canonical sort, duplicates rejected |

#### Every collection facet of `ExecutionContractV1`

| facet | order | 0 elements | Step-4 subset |
|---|---|---|---|
| `dependencies` | set-like (sorted by `name`) | omit | omitted — the subset refuses capsules with dependencies |
| `build_outputs` | set-like (sorted by `name`) | omit | omitted — the subset refuses build outputs |
| `launch.argv` | **ordered** | **required, ≥1** | present |
| `launch.environment` | set-like (sorted by `name`) | omit | omitted when the capsule declares no non-secret value |
| `launch.secret_bindings` | set-like | omit | omitted — Step 4 refuses restore-time bindings (RFC §8.3) |
| `filesystem.readonly_layers` | **ordered** | **required, ≥1** | exactly one (the rootfs layer) |
| `filesystem.writable_paths` | set-like (segment-wise UTF-8 byte order) | omit | omitted or the implicit tmpfs set, per §7 |
| `guest_surface.features` | set-like | omit | omitted (§6.2) |
| `external_state` | set-like (sorted by `name`) | omit | omitted — Step 4 refuses stateful capsules |
| `target.observable_features` | set-like map (sorted by key) | omit | omitted unless the capsule declares one |

**This is a wire-format change, and it is free exactly once.** Today only
`launch.secret_bindings` and `target.observable_features` carry the
omit-when-empty treatment (`skip_serializing_if` + a `present_non_empty_*`
deserializer). The other eight are plain `Vec` and serialize `[]` when empty, so
applying this rule changes their canonical JSON — and therefore the
`execution_id` of any contract with an empty collection.

No contract has ever been minted in production, so nothing is invalidated by
making the change **now**. After the first production mint it becomes a contract
version bump. The existing canonical-JSON test vectors
(`crates/capsule/tests/gen_execution_contract_vectors.rs`) are regenerated as
part of the change.

### 6.4 The v0.3 refusal surface — one entrypoint, one error

Stable error code:

```text
execution_identity_requires_manifest_v1
```

```rust
ExecutionIdentityRequiresManifestV1 {
    found: String,   // the schema_version actually present
}
```

Raised at the **entrance of the shared mint entrypoint**, never partway through
observation — so the refusal is one behaviour in one place rather than a class of
similar-looking failures scattered across the measurement producers.

```text
mint_execution_contract(...)
  ├─ schema_version == "1"  → proceed
  └─ anything else          → ExecutionIdentityRequiresManifestV1 { found }
```

Behaviour by caller:

| caller | behaviour |
|---|---|
| v0.3 `ato run` / `ato build` | never calls the mint entrypoint — current behaviour is untouched |
| v1 `ato build` | mints the contract and records it in `capsule.lock` |
| wizard / publish (contract-required paths) | calls the mint entrypoint as Required; a v0.3 manifest yields the error above |

ato-api does **not** inspect or guess the manifest. It keeps refusing on exactly
what it can see — "the lock carries no `execution_contract`". The explanation of
*why* (the manifest is not v1) is surfaced by the CLI and the Wizard, which are
the parties that can actually read the manifest.

## 7. The Step-4 vertical subset

v1's first landing supports exactly:

- a single-process capsule (no `[services]`, no supervisor);
- no dependencies (until per-dependency digests exist);
- no build outputs;
- no external state (until `[state.<name>] access/schema/mount` lands — note
  Step 4 itself refuses stateful capsules anyway, RFC §8.3);
- one rootfs layer, the no-volume mount topology;
- one guest port, `[web] port` + `[web] bind`;
- `[seal_at] command` required (Step 4 cannot accept a candidate without it).

Everything else is refused with a named error. The subset is chosen so that
every facet in it is `authored`, `resolved`, `measured`, or a normative default
stated in this document — and **nothing in it is approximated**.

---

## 8. Consequences

- Existing v0.3 capsules keep working for `run` / `build` and never mint an
  Execution Identity. Their behaviour is unchanged.
- The Submission Wizard's interactive lane becomes available only to v1
  capsules. The api already refuses to enqueue without a lock-carried contract,
  so this is a narrowing of an already-closed gate, not a new restriction.
- `execution_id` values minted under this ADR are permanent. Every facet in the
  Step-4 subset is traceable to a declaration, a resolution, or a measurement,
  and this document is where a reader checks which.
- **The §6.3 empty-collection rule must land before the first production mint.**
  It changes the canonical JSON of eight facets that currently serialize `[]`,
  and therefore their `execution_id`. Nothing has minted yet, so today it costs a
  vector regeneration; after the first mint it costs a contract version.

### Work this ADR authorizes, in order

1. This ADR, reviewed and accepted.
2. The v1 authoring parser (§7 subset), with unknown fields, duplicates and

3. The config-classification fix (§4.4).
4. The nine payload schemas + measurement producers, with canonical JCS vectors.

   through the normal trusted-load path. `lock_id` and signature boundaries are
   unchanged. — **DONE** (#1142, #1143, #1144); see §9.
6. E2E on real KVM with a v1 fixture **generated by `ato build`** — never
   hand-written. — **DONE** (#1145); evidence in §9.5.

## 9. Outcome of steps 5 and 6

Both are done and verified on real hardware. Two things below CHANGE what §4
classified; they are recorded here rather than edited into §4 so the reason
survives.

### 9.1 What shipped

| step | PR | what it added |
|------|----|---------------|
| 5-1 | #1142 | atomic `capsule.lock` publish (temp → fsync → rename → fsync parent); `into_minted_envelope`, which makes `execution_id` a function of the contract by construction |
| 5-2 | #1143 | `measure_guest_target` (os/arch from `image inspect`, libc probed by running `ldd --version` INSIDE the image, `abi` resolved from the measured libc); the v1 recipe and an init that execs exact argv |
| 5-3 | #1144 | the producer lane: projection → recipe build → guest → measure → observe → mint → persist → trusted-load |
| 6 | #1145 | `filesystem.view_digest` over the guest's contents; the CI reproducibility proof; the KVM E2E harness |

### 9.2 CHANGE: `filesystem.view_digest` commits contents, not the image

§4 classified it as a measurement of "the composed immutable image". Taken
literally — blake3 over the packed ext4 — that value is not reproducible, and
the reason is not a bug that can be fixed:

> Measured on e2fsprogs 1.47.0: `mke2fs` stamps every inode it creates with the
> wall clock and ignores `SOURCE_DATE_EPOCH`. The root inode's `ctime`, `atime`,
> `mtime` and `crtime` were all the mkfs clock; ~9,400 timestamp fields differed
> between two packs of one identical tree. The filesystem UUID, the directory
> hash seed and the superblock clocks were already pinned and did agree.

Byte-identity was reachable — rewrite four timestamps on every inode through
`debugfs` — but it would have made `execution_id` depend on e2fsprogs. An
`apt upgrade` on a builder that changed block allocation would change every
capsule's identity, with no source change and nothing to notice it by. An
identity with that property is not one.

So the facet commits what the guest CONTAINS
(`snapshot::guest_filesystem_digest`): every path, node kind, permission bits
including setuid/setgid/sticky, uid, gid, file content, symlink target and
device numbers, in sorted path order. Not: timestamps, inode numbers, link
counts, block addresses, or the walk order. An undescribable node kind is
refused rather than skipped.

Two ext4 images holding the same files are the same execution however the
allocator laid them out — which is also what anyone means by "the same guest".

**Out of scope for v1, and stated so rather than left to be discovered:**
extended attributes and POSIX ACLs are not read (admitting them must change
`GUEST_FILESYSTEM_VIEW_DOMAIN`); sparse files digest as their contents, which is
what the guest reads; hard links are committed as two paths with equal contents
and the link count is not committed — correct for the read-only roots the
Step-4 subset ships, and owed a revisit by the first lane that allows a writable
root.

The packed image's own digest is still recorded, as a MATERIALIZATION receipt
naming which file a build produced. It is not an identity input, and a test
canonicalizes the contract to assert it appears nowhere in the preimage.

### 9.3 CHANGE: the withheld control-file set does not depend on build history

The projection reports what it removed: the manifest, plus whatever lock the
repository carried. For a PRODUCER that is not stable — this lane WRITES the
lock, so a first build withheld one file and every build after it two, and the
set is identity-bearing. The same program source minted one identity the first
time and a different one forever after.

A v1 build therefore declares the lock withheld whether or not it exists yet: it
is a control file of the workspace either way, because the build is about to
write it. WHICH name is withheld still varies, and still should — a repository
spelling its lock `ato.lock.json` held a different file out than one spelling it
`capsule.lock`.

### 9.4 Confirmed as written

* **`launch.argv` is exact.** The v0.3 bare-`.py` rewrite (`app.py` →
  `python3 app.py`) deliberately does NOT apply: inventing an interpreter would
  put a word in the identity nobody wrote. A word containing a space survives
  into the guest as one argument — see the E2E below.
* **`launch.cwd` is resolved, not authored** (§4.1 lists it `A→R`). The v1
  manifest has no working-directory field and should not gain one: the working
  directory is where the BUILD placed the source.
* **`abi` is resolved from the measured libc**, never defaulted. An
  unclassifiable libc or a non-Linux guest refuses the build.
* **A Git working tree cannot mint an identity.** A root-level `.git` is
  neither a withholdable control file (ADR-014 §1 admits the manifest and the
  one lock, nothing else) nor content whose bytes are reproducible, so the
  workspace is frozen through a content-addressed archive first.

### 9.5 Step 6 evidence

Hetzner CX53, `65.109.37.38`, 2026-07-26. Built by `ato build` from a v1
manifest — never hand-written, as §8 requires.

```text
  second build          blake3:c2257d0d86fcbcb2980b6b07111bd8fef81ae6a907154ef508ee31fb35a06153   (recorded; differs by design)

  committed             ["python3", "server.py", "--label", "step 6"]
  /proc/self/cmdline    ["python3", "server.py", "--label", "step 6"]
application sys.argv    ["server.py", "--label", "step 6"]   (auxiliary; excludes the interpreter)
working directory
  committed             /app
  initial getcwd()      /app
  /proc/self/cwd        /app
```

`launch.argv` is compared against `/proc/self/cmdline` — the vector the kernel
was handed — and not against `sys.argv`. Python drops the interpreter from
`sys.argv`, so that reading can only ever show the application's own arguments:
it demonstrates that `"step 6"` survived as ONE argument, which is worth having,
but it cannot show that `resolved_argv[0]` was honoured at all. Only the full
vector does, and it is what the harness gates on. `sys.argv` is kept above as
auxiliary evidence of the same boundary from the application's side.

`/proc/self/cmdline` is NUL-delimited AND NUL-terminated, so exactly one
trailing empty piece is the terminator and every other one is a real empty
argument. Dropping them all would make `["a", "", "b"]` and `["a", "b"]`
indistinguishable. This capsule has no empty argument — the contract refuses one
— so the harness runs its decoder over crafted input before it builds anything,
and that self-test is what keeps the claim from resting on a reading of the
code.

The working directory is read twice for the same reason: `getcwd()` as the
fixture's first statement is where the process STARTED, `/proc/self/cwd` is
where it IS. A workload that `chdir`'d between them would show as a
disagreement rather than as a pass.

The guest reports its own `sys.argv` and `os.getcwd()`, and the harness compares
them to what `capsule.lock` committed. Not "something answered on :8080" — a
guest serving the right port while running a different argv is exactly the
failure an Execution Identity exists to make impossible, and a readiness probe
cannot see it. `"step 6"` carries a space, so the comparison also shows the
argument boundary survived the guest's shell.

Reproduce with `scripts/e2e/adr015-v1-boot.sh`, which needs
`ATO_STEP6_BOOT_CMD`; it does not guess a firecracker invocation, because a
wrong guess reports the launcher's failure as the capsule's.

### 9.6 What steps 5–6 do NOT cover

Everything outside the §7 subset still has no producer, and `ato#1089` remains
open for it: `build_outputs[]`, `external_state[]`, per-dependency
`(derivation_digest, output_digest)`, `target.observable_features`, and
`runtime.digest` for non-OCI runtimes. `[tools]`, `[[build.steps]]`,
`[state.*]` and non-secret launch-supplied config are refused by
`validate_for_interactive_capture` rather than approximated.
