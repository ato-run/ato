# Runner-owned isolated GUI producer — 2026-10-24

> Status: historical evidence / past plan. Language: en.
> Preserved content; relative navigation updated. Current [documentation map](../../../README.md).

This child implements physical GUI ownership. Pixel lease dispatch, capability
advertisement, API admission and shared Runner installation remain disabled.
No staging, paid provider, operator API key or production operation occurred.

## Execution and trust boundary

The existing Native actor owns an `LaunchedOci::Group`: a trusted display helper
first, then the unchanged application argv. Reverse stop reclaims app, helper
and their internal bridge. Both carry the existing exact Runner/slot/lease/Run
ownership labels, bounded numeric nonroot execution, read-only root, no added
capabilities, no-new-privileges and resource limits. Either workload exiting,
owner EOF, requested stop, idle expiry or maximum lifetime ends the same actor.
The existing stop confirmation/quarantine and label recovery remain authoritative.

The helper is explicit Runner configuration, absent by default. It is a fully
verified immutable OCI archive, outside K/D and outside the Application's service
graph. Its fixed entrypoint creates a new private X server, no host desktop or
window-id selection. It exposes no HTTP, TCP X11, TCP RFB, Docker socket or
management credential. Clipboard is disabled in both directions. Existing
scoped RFB WebSocket gateway/noVNC and bounded capture remain the shared surface.

Only this Run's Unix X11 socket and ephemeral Xauthority directory are mounted
read-only into the app. The helper writes its own socket directories; neither
container sees the host parent. The Runner holds a private loopback-to-Unix RFB
relay with at most eight connections, owned cancellation and no detached copy
threads. A directory-fd alias avoids the Unix socket path length limit.
`DISPLAY`, `XAUTHORITY` and ancestor/descendant mount conflicts are refused.
The helper receives an empty readonly workspace rather than the application source.
The app needs its own GUI libraries, with no TigerVNC, shell wrapper or Ato agent.

The fresh random Xauthority cookie never enters argv, environment values,
receipts, K/D, logs or input/state snapshots. Normal shutdown removes it; an
unconfirmed stop retains only recovery directories, not the cookie. Actual
Runner SIGKILL tested the existing recovery path: after confirmed stops and
before moving the lease into `leases.resolved`, the runtime-only credential is
removed. Symlink parents/lease roots are refused. Saved workspace data survives.

Selected D Port facts are preserved exactly. Pixel can declare two host-owned
`guest_port=None` bindings; the backend refuses missing facts or promised guest
TCP listeners. Existing Some facts, ordinary Web rules and old golden bytes stay
unchanged. Native probe readiness and independently verified original K remain
separate; no ready/K verdict is generated by the producer.

## Render timing discovered by actual execution

Sending a key and immediately requesting a full frame returned the authored
initial blue frame (`be109b2b...b35ad3b7`), so the original green-frame K correctly
failed. The Adapter now admits optional `settle_ms`, omitted/default zero for old
D bytes, at most 1,000ms and strictly within the original operation timeout.
The input runs exactly once, followed by the declared cancellable wait and one
full frame. There is no expected-hash polling, replay, extra deadline or K change.
TCP_NODELAY prevents control-write buffering from consuming this render interval.

The fixture explicitly declares 50ms. Its first g key fills every 640x480 BGRX32
pixel with authored 0x336699; the independently authored expected fingerprint is
`sha256:77bdb4e07f1bb74bb2d0792945dca93918fba26e5adebf9c7c2394a0be95e8e9`.
A second real key, using a separate explicit 200ms test wait, changes the actual
display to red. Repeated probe GETs still return the frozen first result.
The unchanged original Rust K accepts the correct logical probe Port and rejects
the Surface Port or mere readiness bytes.

## CPU fixture and materialization

`tools/native-display-helper` builds from a pinned Ubuntu 24.04 base. Package
fetching occurs only inside its own Docker build; no host packages/services or
shared registry were installed. A second image contains only an independent C
X11 application and its own GUI library. `export-fixture.py` emits tagless archive
transport; Rust verifies the complete manifest/config/layer graph and platform
before any workload resource is created. Optional app archive transport must
match the selected D's exact image and platform. No image/archive is committed.

Actual warm launch: 3,841ms to scoped surface readiness, separately 7,473ms for
verified fixture archive input preparation (debug build). Helper limits were
256MiB/500m CPU/32 PIDs, additional to app 128MiB/500m CPU/32 PIDs. Exact already
loaded config/platform can be reused after complete archive verification. Cache
miss uses the existing bounded offline load; no mutable tag/config-id shortcut or
network fallback is accepted. Hit/miss/wrong-config/wrong-platform tests cover it.

**Cold materialization is not accepted as complete.** Unconditional 123MiB helper
reload exceeded the existing 5s command budget. This PR preserves that per-Run
bound; cold loading can fail safely and needs separate explicit pre-materialization
before rollout. Warm readiness is not a cold-start claim.

## Verification and remaining gates

Actual CPU Docker tests cover scoped gateway reconnect and legacy-scope rejection,
real input/first frame/original K, frozen GET, nonroot/readonly/internal bridge,
all lifecycle stops, timeout, wrong image/platform/archive closure before creation,
partial helper start followed by app spawn failure, and real Runner SIGKILL plus
existing recovery/cookie exclusion. Unit tests cover wire omission, settling
bounds/deadline/cancellation, exact host binding/lowering and symlink refusal.

The existing Web/process/OCI, Terminal dispatch, library, receipt, state and
recovery regressions are checked separately. This is isolated CPU execution,
not staging browser acceptance. Subsequent work must explicitly supply trusted
helper materialization/configuration, connect Pixel dispatch and exact per-D
API/PWA admission, enforce existing same-attempt receipt-gated browser access,
and verify the real app frame before any Pixel capability is advertised.
The dispatch child must also measure trustworthy effective Docker-host/cgroup
capacity and reject app plus helper CPU/RAM overhead before resource creation;
unknown capacity fails closed. This unconnected producer enforces each physical
container's limits but does not yet implement aggregate host admission.
